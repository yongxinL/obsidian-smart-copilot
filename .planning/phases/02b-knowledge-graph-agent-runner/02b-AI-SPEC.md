## 1. System Classification

**System Type:** Autonomous Task Agent (in-process ReAct loop)

**Description:**
A 22-tool in-process ReAct agent that queries the user's personal knowledge vault before any external call. The agent orchestrates typed wikilink graph traversal, hybrid semantic+BM25 retrieval, page CRUD, and background job submission through a thought→action→observation loop bounded to 10 iterations. Users interact via MCP (`brain.query`) or REST (`POST /api/v1/query`); all invocations are persisted in the conversations table with tool traces. "Good" means the agent finds relevant knowledge from the local vault first, returns grounded answers with citations, and respects the brain-first discipline without fabricating information absent from the vault.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. **External API call before local brain check** — agent invokes web search or external API before exhausting `brain.search` and `brain.graph.traverse` (violates D-06 brain-first discipline)
2. **Infinite iteration / runaway loop** — agent exceeds 10 ReAct iterations without returning a result (must return `status: max_iterations_reached` with best partial answer at limit)
3. **Silent tool failure swallowed** — a critical tool failure (auth error, schema error) is silently absorbed rather than aborting the loop, causing a fabricated response
4. **Non-retryable error retried** — agent retries a 401 auth error or schema validation error (should abort, not retry), burning iterations and leaking cost
5. **Conversation not persisted** — a `brain.query` invocation via MCP or REST does not create/append a conversation record (parity gap between transports, violates D-08)

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Personal Knowledge Management (PKM) / Second Brain tooling for knowledge workers

**User Population:** Developers, researchers, and consultants who maintain private vaults of notes, meeting records, ideas, and research snippets. They use the system daily via Claude Desktop, Claude Code, or Hermes as MCP clients. They have high expectations for recall precision — the vault is their own mental model materialised, and they know its content.

**Stakes Level:** High

**Output Consequence:** The user acts on agent answers to recall people, decisions, project history, and research context. A fabricated answer about a person in the vault ("John Smith works at Acme Corp") that contradicts what the user wrote may cause the user to misrepresent facts in a meeting or email. Because the source is the user's own notes, incorrect answers erode trust in the system faster than in general-purpose AI — the user knows the ground truth.

### What Domain Experts Evaluate Against

---

**Dimension: Vault-grounded recall — the answer matches what the user actually wrote**

Good (expert accepts): Response cites the specific page slug and states only facts present in the retrieved vault content. If the vault says "John Smith joined Acme Corp in March 2024", the answer says exactly that.

Bad (expert flags): Response states a fact about a person or company that is not in any retrieved page — e.g., adding a job title or relationship the user never recorded. This is the PKM-specific hallucination: the system fills gaps in vault content with model priors rather than admitting the vault has no record.

Stakes: Critical

Source: PKM practitioner expectations (Sebastien Dubois, "Your AI Doesn't Know You", 2025); AGENT-02 requirement (agent MUST query local brain before any external call); D-06 brain-first discipline.

---

**Dimension: Citation traceability — user can verify every claim**

Good (expert accepts): Every factual claim in the answer includes an inline reference to the source page slug (e.g., `[john-smith]`, `[acme-corp-meeting-2024-03]`). The user can navigate to that page and confirm the information.

Bad (expert flags): Answer states facts without citing which page they came from, making it impossible to verify. Or answer cites a page that does not contain the stated fact (mis-citation).

Stakes: Critical

Source: PKM practitioner standard — the "second brain" value proposition depends on traceability back to the original source. Equivalent to citation standards in legal and academic domains. Aligns with AGENT-05 (citations column on messages table).

---

**Dimension: Empty-vault transparency — the system knows what it does not know**

Good (expert accepts): When the vault has no relevant pages, the agent returns a clear structured response: "No local knowledge found for [query]. You can add relevant pages or ask to use external sources." The user understands there is a gap and knows how to fill it.

Bad (expert flags): Agent returns a plausible-sounding answer synthesised from model training data when the vault is empty on the topic. The user cannot distinguish this from a vault-grounded answer. This is the most trust-destroying failure in PKM systems.

Stakes: Critical

Source: D-06 brain-first discipline (Phase 2b context decisions); PKM practitioner research — "generic output despite effort" is identified as the primary trust-breaking failure mode (Sebastien Dubois, 2025); Personal LLM Agents survey (Li et al., arxiv:2401.05459) — hallucination during task completion identified as the primary reliability failure.

---

**Dimension: Graph relationship accuracy — typed edges reflect what the user established**

Good (expert accepts): For a query like "who works at Acme Corp?", the agent traverses the `works_at` typed edges from the knowledge graph and returns only the persons whose vault page contains an explicit `employer: [[Acme Corp]]` frontmatter edge. Edge type is stated ("according to your vault").

Bad (expert flags): Agent infers or invents employment relationships from prose context ("the notes mention John attended an Acme meeting") without the user having explicitly recorded an edge. Or agent merges two entities that have different canonical slugs without stating the merge assumption.

Stakes: High

Source: GRAPH-01 through GRAPH-06 requirements; PersonalAI knowledge graph evaluation research (arxiv:2506.17001) — relevance vs completeness trade-off and information staleness identified as primary graph retrieval failure modes.

---

**Dimension: Query response completeness — multi-entity queries return all relevant vault entries**

Good (expert accepts): For "what did I write about machine learning last month?", the agent returns all pages tagged or linked to the concept within the date range — not just the first match. If there are 5 relevant pages, all 5 are referenced with their dates.

Bad (expert flags): Agent returns 1-2 matches and presents the answer as complete, when 3-5 more relevant pages exist in the vault. The user later discovers the missing entries themselves. This is the PKM-specific retrieval incompleteness failure — distinct from generic recall because the user's vault is finite and they expect exhaustive coverage on their own notes.

Stakes: High

Source: PersonalAI research (arxiv:2506.17001) — "NoAnswer" outputs occur in 16-73% of configurations; PKM practitioner criterion: "compound improvement — system gets better the longer you use it" (Sebastien Dubois, 2025); AGENT-06 golden query eval suite with Recall@K metric.

### Known Failure Modes in This Domain

1. **Vault gap hallucination** — the agent fills missing vault content with model training priors. Manifests as: the user asks about a person they have sparse notes on, and the agent returns a plausible but fabricated job history or company affiliation. Unlike general-purpose hallucination, the user has high confidence the vault should have the answer and may not check. This is the highest-trust-cost failure in PKM systems.

2. **Entity conflation across canonical slugs** — two distinct entities in the vault share similar names (e.g., "John Smith" at Acme vs "John Smith" at Beta Corp). The agent merges them into a single answer without stating the ambiguity. The user gets a mixed response that contaminates their knowledge model.

3. **Stale note surfaced as current** — the vault contains both an old meeting note and a newer one for the same person/project. The agent retrieves the older page (higher BM25 score due to keyword density) and presents outdated information without noting the date or the existence of a more recent entry. Knowledge workers frequently update notes; temporal ordering of results matters.

4. **Brain-first discipline bypass** — for queries that appear to require current information (e.g., "what is the latest funding round for Acme Corp?"), the agent skips local vault search and calls a web tool directly, presenting external results as if they were grounded in the vault. The user loses the boundary between their personal knowledge and external data.

### Regulatory / Compliance Context

**GDPR / EU AI Act (directly relevant for EU-based users and deployments):**

The vault contains personal data: person pages include names, employers, relationships, and notes about meetings. Under GDPR Article 4, this constitutes personal data processing. Relevant constraints:

- **Data minimisation**: The agent must not send vault content to external providers unless the user has explicitly requested external enrichment. The brain-first architecture (D-06) enforces this by design — local retrieval is always attempted first.
- **Local-only deployment option**: The system's single-Docker, homelab-friendly deployment model means vault data can be kept entirely on-premises, which satisfies GDPR's data residency and data minimisation requirements without additional controls. This is an architectural privacy benefit.
- **No training data exfiltration**: Vault content sent to LLM providers (for the ReAct loop) should be treated as personal data. The system uses per-user encrypted provider keys (AUTH-09) and does not share vault content across users (RLS enforcement via VAULT-02). No vault content is used for model training under the provider terms applicable to API usage.
- **EU AI Act (August 2026 deadline)**: This system is a personal productivity tool, not a high-risk AI system under Annex III of the EU AI Act. No biometric data, no employment decisions, no critical infrastructure. The Act's general transparency requirements apply: users should be able to understand when the agent is operating on vault content vs. admitting no local knowledge exists.

**No HIPAA, FCA, or SOC 2 obligations identified** for this deployment context (personal productivity tool, not a regulated healthcare, financial, or enterprise SaaS system).

## 2. Framework Decision

**Selected Framework:** Pure Python ReAct (LiteLLM `tool_use` API)

**Version:** LiteLLM ≥ 1.35.0 (already in requirements from Phase 2a)

**Rationale:**
Given the hard requirements for a custom iteration counter (D-05: max 10), retryable/non-retryable error classification (D-07), and brain-first sequencing (D-06), a hand-rolled ReAct loop over `litellm.acompletion()` gives full deterministic control over every state transition — no framework internals to fight or paper over. Zero new dependencies keeps Phase 2a's LiteLLM as the only AI layer, and the 22-tool surface maps cleanly to the OpenAI-style `tools=` parameter that LiteLLM normalises across providers. The entire loop fits in ~200 lines of Python.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Pydantic AI | Adds typed tool dispatch but introduces a new dep with its own async runtime; the loop is simple enough that typed dispatch is not worth the abstraction cost at 22 tools |
| LangGraph | Graph-based checkpointing is valuable for long-running workflows but the in-process ReAct loop here is bounded to 10 iterations — the overhead of LangGraph's graph compilation and state schemas exceeds the benefit |
| LlamaIndex Agents | Opinionated about retrieval integration; would conflict with Phase 2a's custom hybrid search service and obscure the brain-first discipline |

**Vendor Lock-In Accepted:** No — LiteLLM already abstracts provider APIs; swapping the underlying model requires only a router config change

### Entry Point Pattern

The complete bounded ReAct loop. Copy-paste runnable — annotated inline for every D-0x decision.

```python
"""server/app/agent/react_loop.py — bounded ReAct loop over litellm.acompletion."""
from __future__ import annotations

import json
import uuid
from typing import Any

import structlog
from litellm import acompletion
from litellm.exceptions import (
    AuthenticationError,
    BadRequestError,
    RateLimitError,
    ServiceUnavailableError,
    Timeout,
)
from pydantic import ValidationError

from app.agent.models import AgentResponse, ToolTrace
from app.agent.tools import TOOL_REGISTRY, TOOL_SPECS   # 22-tool registry
from app.agent.prompts import BRAIN_FIRST_SYSTEM_PROMPT
from app.auth.context import OperationContext

log = structlog.get_logger("smart_copilot.agent.react_loop")

# D-05: hard iteration ceiling
MAX_ITERATIONS = 10

# D-07: classify exceptions before attempting retry
_RETRYABLE = (Timeout, ServiceUnavailableError, RateLimitError)
_NON_RETRYABLE = (AuthenticationError, BadRequestError)

# D-07: tools that the loop may skip (continue) on failure
_NON_CRITICAL_TOOLS = frozenset({
    "brain.graph.traverse",
    "query.expand",
    "entity.enrich",
})


async def run_react_loop(
    query: str,
    op_ctx: OperationContext,
    model: str = "anthropic/claude-sonnet-4-6",
    api_key: str | None = None,
) -> AgentResponse:
    """
    Execute a bounded ReAct loop (thought -> action -> observation).

    Returns an AgentResponse with status, answer, and tool_traces.
    Never raises — all errors are captured into the response.
    """
    messages: list[dict] = [
        {"role": "system", "content": BRAIN_FIRST_SYSTEM_PROMPT},
        {"role": "user", "content": query},
    ]
    traces: list[ToolTrace] = []
    warnings: list[str] = []
    iteration = 0

    while iteration < MAX_ITERATIONS:
        iteration += 1
        log.debug("react_iteration_start", iteration=iteration, query=query[:80])

        # --- THINK: call LLM with full tool list ---
        try:
            response = await acompletion(
                model=model,
                messages=messages,
                tools=TOOL_SPECS,           # OpenAI-format list of 22 tool defs
                tool_choice="auto",
                max_tokens=2048,
                temperature=0.0,            # deterministic reasoning
                api_key=api_key,
                metadata={"user_id": str(op_ctx.user_id)},
            )
        except _RETRYABLE as exc:
            log.warning("react_llm_retryable", error=str(exc), iteration=iteration)
            # Retry once (same messages)
            try:
                response = await acompletion(
                    model=model,
                    messages=messages,
                    tools=TOOL_SPECS,
                    tool_choice="auto",
                    max_tokens=2048,
                    temperature=0.0,
                    api_key=api_key,
                    metadata={"user_id": str(op_ctx.user_id)},
                )
            except Exception as retry_exc:
                return AgentResponse(
                    status="tool_error",
                    answer=None,
                    tool_traces=traces,
                    warnings=warnings,
                    error=f"LLM call failed after retry: {retry_exc}",
                )
        except _NON_RETRYABLE as exc:
            # D-07: auth/schema errors abort immediately
            return AgentResponse(
                status="tool_error",
                answer=None,
                tool_traces=traces,
                warnings=warnings,
                error=f"Non-retryable LLM error: {exc}",
            )

        assistant_msg = response.choices[0].message
        tool_calls = assistant_msg.tool_calls or []

        # --- FINISH: no tool calls = final answer ---
        if not tool_calls:
            answer_text = assistant_msg.content or ""
            return AgentResponse(
                status="success" if not warnings else "success_with_warnings",
                answer=answer_text,
                tool_traces=traces,
                warnings=warnings,
            )

        # Append assistant message (with tool_calls embedded) to history
        messages.append({
            "role": "assistant",
            "content": assistant_msg.content,
            "tool_calls": [
                {
                    "id": tc.id,
                    "type": "function",
                    "function": {
                        "name": tc.function.name,
                        "arguments": tc.function.arguments,
                    },
                }
                for tc in tool_calls
            ],
        })

        # --- ACT + OBSERVE: dispatch each tool call ---
        for tc in tool_calls:
            tool_name = tc.function.name
            try:
                tool_args = json.loads(tc.function.arguments)
            except json.JSONDecodeError:
                tool_args = {}

            observation = await _dispatch_tool(
                tool_name=tool_name,
                tool_args=tool_args,
                op_ctx=op_ctx,
                traces=traces,
                warnings=warnings,
                tc_id=tc.id,
            )

            # Check if dispatch signalled a critical abort
            if observation is None:
                return AgentResponse(
                    status="tool_error",
                    answer=None,
                    tool_traces=traces,
                    warnings=warnings,
                    error=f"Critical tool '{tool_name}' failed — aborting loop.",
                )

            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,
                "name": tool_name,
                "content": json.dumps(observation),  # observation fed back as string
            })

    # --- D-05: max iterations reached ---
    log.warning("react_max_iterations_reached", query=query[:80])
    # Extract best partial answer from last assistant content if any
    last_content = ""
    for msg in reversed(messages):
        if msg["role"] == "assistant" and msg.get("content"):
            last_content = msg["content"]
            break
    return AgentResponse(
        status="max_iterations_reached",
        answer=last_content or None,
        tool_traces=traces,
        warnings=warnings,
    )


async def _dispatch_tool(
    tool_name: str,
    tool_args: dict,
    op_ctx: OperationContext,
    traces: list[ToolTrace],
    warnings: list[str],
    tc_id: str,
) -> dict | None:
    """
    Call the named tool, apply D-07 error classification, record trace.
    Returns observation dict, or None to signal a critical abort.
    """
    tool_fn = TOOL_REGISTRY.get(tool_name)
    if tool_fn is None:
        # Unknown tool — treat as non-critical skip
        obs = {"error": f"unknown tool: {tool_name}"}
        traces.append(ToolTrace(tool_call_id=tc_id, tool_name=tool_name,
                                args=tool_args, observation=obs, retried=False,
                                skipped=True, skip_reason="unknown_tool"))
        warnings.append(f"Unknown tool '{tool_name}' skipped")
        return obs

    retried = False
    for attempt in range(2):  # at most 2 attempts (original + 1 retry)
        try:
            result = await tool_fn(op_ctx=op_ctx, **tool_args)
            traces.append(ToolTrace(tool_call_id=tc_id, tool_name=tool_name,
                                    args=tool_args, observation=result,
                                    retried=retried, skipped=False))
            return result

        except _RETRYABLE as exc:
            if attempt == 0:
                # D-07: retry once on transient errors
                log.warning("tool_retryable_error", tool=tool_name, error=str(exc))
                retried = True
                continue
            # Second attempt also failed — classify by criticality
            observation = {"error": "retryable_failure", "detail": str(exc)}
            traces.append(ToolTrace(tool_call_id=tc_id, tool_name=tool_name,
                                    args=tool_args, observation=observation,
                                    retried=True, skipped=tool_name in _NON_CRITICAL_TOOLS,
                                    skip_reason="retryable_exhausted"))
            if tool_name in _NON_CRITICAL_TOOLS:
                warnings.append(f"Non-critical tool '{tool_name}' failed (transient); skipped")
                return observation
            # Critical tool failed — signal abort
            return None

        except _NON_RETRYABLE as exc:
            # D-07: never retry auth/validation errors
            observation = {"error": "non_retryable_failure", "detail": str(exc)}
            traces.append(ToolTrace(tool_call_id=tc_id, tool_name=tool_name,
                                    args=tool_args, observation=observation,
                                    retried=False, skipped=tool_name in _NON_CRITICAL_TOOLS,
                                    skip_reason="non_retryable"))
            if tool_name in _NON_CRITICAL_TOOLS:
                warnings.append(f"Non-critical tool '{tool_name}' failed (auth/schema); skipped")
                return observation
            log.error("critical_tool_non_retryable", tool=tool_name, error=str(exc))
            return None   # critical abort

        except Exception as exc:  # noqa: BLE001
            observation = {"error": "unexpected_failure", "detail": str(exc)}
            traces.append(ToolTrace(tool_call_id=tc_id, tool_name=tool_name,
                                    args=tool_args, observation=observation,
                                    retried=retried, skipped=tool_name in _NON_CRITICAL_TOOLS,
                                    skip_reason="unexpected"))
            if tool_name in _NON_CRITICAL_TOOLS:
                warnings.append(f"Non-critical tool '{tool_name}' unexpected error; skipped")
                return observation
            return None   # critical abort

    return None  # unreachable; satisfies type checker
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `acompletion(tools=, tool_choice="auto")` | Async LLM call with OpenAI-format tool definitions. LiteLLM normalises this across OpenAI, Anthropic, DeepSeek. Returns `response.choices[0].message.tool_calls` (list) or `None` (final answer). | Every iteration of the ReAct loop — both the THINK step and the FINISH detection. |
| `tool_calls[i].function.name / .arguments` | LiteLLM parses the model's JSON tool call into a structured object. `.arguments` is a raw JSON string — you must `json.loads()` it yourself. | During the ACT step to identify which tool to call and with which kwargs. |
| `role: "tool"` message with `tool_call_id` | The observation message format. Must include `tool_call_id` matching the `tc.id` from the assistant message, or the next LLM call will raise a `BadRequestError` on most providers. | After every tool dispatch — feeds the observation back into the message history. |
| `_RETRYABLE` / `_NON_RETRYABLE` exception classes | `litellm.exceptions` maps provider-specific HTTP errors to typed Python exceptions. `Timeout` + `ServiceUnavailableError` + `RateLimitError` are retryable; `AuthenticationError` + `BadRequestError` are not. | D-07 error classification — determines retry vs abort vs skip. |
| `TOOL_REGISTRY` dict | Maps tool name strings (e.g., `"brain.search"`) to async callables. Decoupled from tool specs so the LLM tool definition list and the dispatch table evolve independently. | `_dispatch_tool()` lookup. Register all 22 tools at app startup. |

### Common Pitfalls

1. **Missing `tool_call_id` on observation message** — Appending a `role: "tool"` message without the matching `tool_call_id` causes OpenAI and Anthropic providers to reject the next request with a 400 `BadRequestError`. Every observation message must carry the exact `tc.id` from the corresponding assistant tool_call. Verified from LiteLLM docs `docs/completion/function_call` and `docs/reasoning_content`.

2. **Appending assistant message without `tool_calls` field when tool_calls exist** — When the model returns tool calls, the assistant message appended to history must include the `tool_calls` list in OpenAI format. Omitting it and only appending `content` causes the provider to reject the follow-up call with a message history validation error. Pattern: always reconstruct the dict explicitly (see entry point above) — do not pass the raw `ModelResponse` object.

3. **`json.loads()` failure on malformed `arguments`** — Providers occasionally emit malformed JSON in `tool_call.function.arguments` (especially on the first iteration when the model is still calibrating). Wrap in a `try/except json.JSONDecodeError` and fall back to `{}` — the tool will fail gracefully and the observation will surface the error. Do not let a JSONDecodeError abort the loop.

4. **Iteration counter not incremented before the LLM call** — If you increment `iteration` at the bottom of the loop body (not the top), you burn one extra LLM call beyond the limit. D-05 requires the check to happen before the acompletion call, not after.

5. **Running sync `litellm.completion()` inside an async FastAPI route** — LiteLLM's sync `completion()` calls `asyncio.run()` internally, which raises `RuntimeError: This event loop is already running` inside uvicorn. The ReAct loop is always called from a FastAPI route handler — always use `acompletion()`. The same applies to any tool implementation that calls LiteLLM internally.

```python
CHEAP_MODEL = "openai/gpt-4o-mini"       # query classification, intent routing
```

**Core Pattern:**

The ReAct loop accumulates a `messages` list across iterations. Each iteration appends:
1. The assistant message (which may contain `tool_calls`)
2. One `role: "tool"` observation message per tool call dispatched

The loop terminates when either: (a) the model returns no `tool_calls` (final answer), or (b) `iteration == MAX_ITERATIONS` (D-05 ceiling). Tool dispatch is a separate coroutine (`_dispatch_tool`) that encapsulates D-07 error classification so the main loop stays linear and readable.

D-06 brain-first is enforced in the system prompt, not in code. The system prompt instructs: "Always call `brain.search` first. If results are empty, call `brain.graph.traverse`. If still empty, return `{status: no_local_knowledge}` and stop. Never call external APIs without explicit user request." This is declarative enforcement — the iteration counter and error handling are code-level. Testing the brain-first rule requires an eval suite (golden queries) that exercises the empty-vault path.

**Tool Use:**

The 22 tools are registered in `TOOL_SPECS` as a list of OpenAI-format dicts:

```python
# server/app/agent/tools/__init__.py
```

Tool implementations are thin async wrappers that call the existing `services/` layer via `session_with_rls(ctx)`. They do NOT embed business logic — they just translate tool args into service calls and return the service response dict. This keeps the tools unit-testable without an LLM.

**State Management:**

The `messages` list is the sole in-memory state for a single agent invocation. It is never persisted mid-loop. On completion, the service layer persists:
- `conversations` + `messages` table: user message + final assistant response only (D-11). Intermediate thought/action pairs are NOT written here.
- `tool_traces` storage (D-12): the `traces: list[ToolTrace]` accumulated during the loop is written as JSONB on the `messages` row (or a separate `tool_traces` table if independent querying is needed — planner decides). Referenced by `message_id` for Phase 4 memory extraction.

```python
# server/app/services/agent_service.py
async def persist_agent_invocation(
    op_ctx: OperationContext,
    session_id: uuid.UUID | None,
    user_query: str,
    result: AgentResponse,
) -> uuid.UUID:
    """Write user message + assistant response to DB. Return message_id."""
    async for session in session_with_rls(op_ctx):
        # Upsert conversation (D-09: session_id provided -> append; else new)
        conv = await get_or_create_conversation(session, op_ctx, session_id)
        msg = Message(
            conversation_id=conv.id,
            role="user",
            content=user_query,
            citations=[],
            tool_calls=[],
        )
        session.add(msg)
        await session.flush()

        assistant_msg = Message(
            conversation_id=conv.id,
            role="assistant",
            content=result.answer or "",
            citations=_extract_citations(result.tool_traces),
            tool_calls=[t.model_dump() for t in result.tool_traces],  # D-12
        )
        session.add(assistant_msg)
        await session.commit()
        return assistant_msg.id
```

**Context Window Strategy:**

A ReAct loop with 10 iterations accumulates messages aggressively. Estimate at each iteration:
- System prompt: ~500 tokens (brain-first instructions + tool descriptions for 22 tools ~3,000 tokens)
- Tool spec list (22 tools passed every call): ~2,000–3,000 tokens (the largest fixed cost)
- Per-iteration pair (assistant + tool observation): ~200–500 tokens
- After 10 iterations: ~500 + 3,000 + 10×500 = ~8,500 tokens input

For `claude-sonnet-4-6` (200K context) this is trivially within limits. However, for models with smaller context windows (e.g., `gpt-4o-mini` at 128K, or future smaller models), apply the following strategy:

1. **Tool spec pruning**: After iteration 3, if `brain.search` has already returned results, remove `brain.search` from the `tools=` list for subsequent calls (reduces fixed overhead by ~200 tokens per call).
2. **Observation truncation**: Cap each tool observation at 4,000 characters before appending to messages. Append `"[truncated — full result in trace]"` marker. The full result is still in `traces` for debugging.
3. **Never summarise mid-loop**: Summarising intermediate steps introduces hallucination risk. Truncation + removal is safer.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. All examples are specific to Pure Python ReAct + LiteLLM `tool_use` for an autonomous in-process agent.

### 4b.1 Structured Outputs with Pydantic

LiteLLM does not enforce Pydantic schemas on tool arguments or final answers natively. For this agent there are two structured output surfaces:

**1. AgentResponse — the agent's final return value (always Pydantic-validated):**

```python
# server/app/agent/models.py
from __future__ import annotations
from typing import Any, Literal
from pydantic import BaseModel, Field


class ToolTrace(BaseModel):
    """One thought-action-observation cycle."""
    tool_call_id: str
    tool_name: str
    args: dict[str, Any]
    observation: dict[str, Any]
    retried: bool = False
    skipped: bool = False
    skip_reason: str | None = None


class AgentResponse(BaseModel):
    """
    Final agent output persisted to messages + tool_traces (D-11, D-12).

    status:
      "success"                — answer grounded in local vault
      "success_with_warnings"  — answer returned but non-critical tool(s) failed
      "tool_error"             — critical tool failure; no answer
      "max_iterations_reached" — hit D-05 ceiling; partial answer may be present
      "no_local_knowledge"     — D-06 brain-first exhausted with no results
    """
    status: Literal[
        "success",
        "success_with_warnings",
        "tool_error",
        "max_iterations_reached",
        "no_local_knowledge",
    ]
    answer: str | None = None
    tool_traces: list[ToolTrace] = Field(default_factory=list)
    warnings: list[str] = Field(default_factory=list)
    error: str | None = None
```

**2. `brain.query` tool call arguments — validated before dispatch:**

The 22 tool wrappers each define a Pydantic input model. Validation happens in `_dispatch_tool()` before calling the service, so a malformed tool call from the LLM surfaces as a `BadRequestError`-like trace rather than crashing the loop:

```python
# server/app/agent/tools/brain.py
from pydantic import BaseModel, field_validator

class BrainSearchArgs(BaseModel):
    query: str
    limit: int = 10

    @field_validator("query")
    @classmethod
    def non_empty(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("query must be non-empty")
        return v

    @field_validator("limit")
    @classmethod
    def clamp_limit(cls, v: int) -> int:
        return max(1, min(v, 100))

async def brain_search_tool(op_ctx: OperationContext, **kwargs: Any) -> dict:
    try:
        args = BrainSearchArgs(**kwargs)     # validates before any DB call
    except ValidationError as exc:
        return {"error": "validation_error", "detail": exc.errors()}
    # ... call services/search.py hybrid_search(args.query, args.limit)
```

**Retry logic for structured output validation:**
- Tool argument validation errors (malformed LLM output) are recorded as observations with `error: "validation_error"`. The loop does not retry — the model sees the error in the next observation and corrects its argument.
- For the final `AgentResponse`, Pydantic validation is structural (not LLM-generated) so it cannot fail unless the code has a bug. No retry needed.
- If the loop exits with no answer content and `status: "success"`, that is a logic bug — add an assertion: `assert result.answer is not None or result.status != "success"`.

### 4b.2 Async-First Design

LiteLLM's `acompletion()` uses `httpx.AsyncClient` internally and is a true coroutine. The entire ReAct loop must run in the same async context.

**The one common mistake in this setup:**

```python
# WRONG — do NOT do this inside a FastAPI route (uvicorn runs its own event loop)
def query_endpoint(request: QueryRequest):
    result = asyncio.run(run_react_loop(request.query, op_ctx))   # raises RuntimeError
    return result

# CORRECT — FastAPI route must be async; the loop is awaited directly
@router.post("/api/v1/query")
async def query_endpoint(request: QueryRequest, op_ctx: OperationContext = Depends(get_op_ctx)):
    result = await run_react_loop(request.query, op_ctx)
    await persist_agent_invocation(op_ctx, request.session_id, request.query, result)
    return result.model_dump()
```

**Stream vs await for this agent:**

Do NOT stream the ReAct loop. Each iteration needs the complete response to check `tool_calls` before deciding whether to dispatch tools or return the answer. Streaming with `acompletion(stream=True)` would require accumulating all chunks before parsing `tool_calls` — you get the overhead of streaming with none of the UX benefit.

Stream only for the final synthesis step if you add a Phase 3 answer synthesis pass that streams tokens to the client. The ReAct loop itself always uses `await acompletion(stream=False)`.

**Tool implementations must be async throughout:** Each tool wrapper is `async def` and calls services via `async for session in session_with_rls(ctx)`. Never call `asyncio.run()` inside a tool implementation — it will raise `RuntimeError` since the loop is already running inside the ReAct loop which runs inside a FastAPI request handler.

### 4b.3 Prompt Engineering Discipline

```python
# server/app/agent/prompts.py
# System prompt: immutable contract — never constructed at runtime via f-string.
# Defines: brain-first ordering (D-06), iteration discipline, response format.
BRAIN_FIRST_SYSTEM_PROMPT = """You are the Smart Copilot agent with access to the user's personal knowledge vault.

BRAIN-FIRST DISCIPLINE (mandatory):
1. Always call brain.search first with the user's query.
2. If brain.search returns empty results, call brain.graph.traverse with the key entity.
3. If both return empty, respond with: {"status": "no_local_knowledge", "message": "No local knowledge found for [query]. You can add relevant pages or ask to use external sources."}
4. NEVER call external APIs, web search, or any tool outside the brain.* and graph.* namespaces without explicit user permission.

TOOL USE RULES:
- Call at most one tool per iteration unless results clearly depend on each other.
- Include citations (page slug + chunk_id) in your final answer whenever referencing vault content.
- When you have enough information, return your answer directly — do not call more tools.

RESPONSE FORMAT:
Return a natural-language answer grounded in vault content. Include slug references like [page-slug] inline."""

# User prompt: carries only the query — no instructions (those live in system)
# Never append instructions to the user message — it confuses role separation.
```

Token budget per call:
- System prompt: ~350 tokens
- Tool specs (22 tools): ~2,500–3,000 tokens (dominant fixed cost; see context window strategy)
- User query: ≤ 200 tokens
- Per-observation content: cap at 4,000 chars (~1,000 tokens) before appending to messages

Few-shot guidance: Do NOT add few-shot examples inline in the system prompt. The prompt is already long from 22 tool definitions. If tool selection quality is poor after eval, add 2–3 few-shot turn examples as `{"role": "user"} / {"role": "assistant"} / {"role": "tool"}` message triplets prepended to `messages` before the actual user query. Retrieve them dynamically from a small fixture file rather than hardcoding in the prompt constant.

### 4b.4 Context Window Management

For an autonomous ReAct agent, the dominant context management concern is iteration accumulation:

**Observation truncation (apply from iteration 1):**
```python
MAX_OBSERVATION_CHARS = 4_000

def _truncate_observation(obs: dict) -> dict:
    """Cap string values in the observation to stay within context budget."""
    text = json.dumps(obs)
    if len(text) <= MAX_OBSERVATION_CHARS:
        return obs
    # Truncate at character level — safe for JSON values
    truncated = text[:MAX_OBSERVATION_CHARS]
    return {"_truncated": True, "content": truncated, "_note": "full result in tool_traces"}
```

**Tool spec pruning (apply after iteration 3 when vault has results):**
Once `brain.search` has returned results (detectable from traces), remove retrieval tools from the `tools=` list for the remaining iterations. The model already has the retrieval results as observations — re-presenting retrieval tools wastes ~500 tokens per call and can cause the model to re-search unnecessarily.

**Why compaction frameworks (LangGraph, Claude SDK) are not used here:**
The loop is bounded to 10 iterations. Even in the worst case (10 iterations × 500 tokens/pair + 3,000 token tool spec overhead) the total context stays under 10K tokens — well within any production model's limit. Compaction/summarisation would introduce hallucination risk for no benefit at this scale.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Iteration ceiling (D-05)** | `iteration == MAX_ITERATIONS` at top of ReAct loop | Return `AgentResponse(status="max_iterations_reached", answer=last_assistant_content_or_None)`. Never silently exceed. Span attribute `agent.terminated_reason="max_iterations"`. |
| **Critical tool abort (D-07)** | `_dispatch_tool()` returns `None` for a critical tool (auth/schema/unexpected on `brain.search`, `brain.get`, `brain.put`) | Return `AgentResponse(status="tool_error", answer=None, error=...)`. Never proceed to next iteration with an unrecorded critical failure. |
| **Non-retryable error abort (D-07)** | Tool raises `AuthenticationError` or `BadRequestError` | Do NOT retry. Record trace with `skip_reason="non_retryable"`. If critical tool → abort loop with `tool_error`. If non-critical → continue with warning. |
| **External tool gate (D-06)** | Agent attempts to invoke any tool outside `brain.*`, `graph.*`, `entity.lookup` AND `brain.search` has not yet been called in this invocation | Reject tool dispatch with synthetic observation `{"error": "brain_first_violation", "detail": "call brain.search before external tools"}`; record in trace. Forces model to course-correct on the next iteration. (Phase 5 will relax this when `@web` prefix is parsed.) |
| **Provider key scrub** | Every `acompletion()` call's `api_key` kwarg before logging or telemetry | Inherit Phase 2a's scrubber: redact key from all log output, span attributes, and `llm_usage` rows. Log `[REDACTED]`. |
| **RLS enforcement** | Every DB session inside a tool dispatch (`session_with_rls(op_ctx)`) | `SET app.current_user_id` + `RESET` in `finally:` — reject DB query if session lacks user_id. Any RLS-failed query raises and is classified as critical → abort loop. |
| **Tool argument validation** | Every tool dispatch — Pydantic args model validates kwargs before service call | On `ValidationError`, return observation `{"error": "validation_error", "detail": exc.errors()}`. Loop continues — model sees the error in next observation and self-corrects. Do NOT retry the same args. |
| **Cost ceiling per invocation** | Cumulative `llm_usage.cost_usd` for the conversation_id exceeds `$0.10` mid-loop | Inject synthetic observation `{"warning": "cost_ceiling_approached", "detail": "respond with current information"}` on next iteration; do NOT abort. Phoenix span attribute `agent.cost_ceiling_hit=true`. |
| **Empty result handling (D-06)** | `brain.search` returns 0 results AND `brain.graph.traverse` returns 0 results in the same loop | Loop is permitted to terminate with `status="no_local_knowledge"` and canonical message; model is instructed via system prompt to do so. Code-level safety net: if 4 iterations pass with both tools returning empty, force-terminate with `no_local_knowledge` to prevent the agent from drifting into external calls or fabrication. |
| **Conversation persistence parity (D-08)** | Every agent invocation via either MCP `brain.query` or REST `POST /api/v1/query` | Both transports invoke `persist_agent_invocation()` after the loop returns. Integration test asserts row creation on both paths under identical inputs. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Golden query suite pass rate** | Run full suite weekly + on every prompt/model change | If any Critical dimension fails OR any High dimension regresses ≥5% vs baseline: block release; investigate the failing query; either fix the agent or update baseline with rationale. |
| **Iteration count distribution** | Daily aggregate of `len(tool_traces)` across all production `brain.query` invocations | If p50 drifts above 4 OR p95 above 7, the model is thrashing on tool selection — investigate prompt drift, tool description quality, or model version. |
| **`no_local_knowledge` ratio** | Daily aggregate of `result.status == "no_local_knowledge"` / total agent invocations | If ratio drops below 5% for a vault with known sparse topics, the agent may be confabulating instead of returning `no_local_knowledge` — sample 10 recent `success` responses and human-review for vault-groundedness. If ratio rises above 50%, the retrieval pipeline is broken — investigate Phase 2a hybrid search health. |
| **Tool failure rate by tool** | Daily aggregate of `traces` with `skipped=true` or `retried=true`, grouped by `tool_name` | If `brain.graph.traverse` fails >10% of invocations, the recursive CTE may be regressing on large graphs. If `entity.enrich` fails >20%, the tool may need to be downgraded to Phase 3-only. |
| **Citation density** | Weekly sample: 50 random `status=success` messages; LLM-judge whether every factual sentence has an inline `[slug]` | If <90% of sentences carry citations, system prompt drift — add a `--strict-citation` mode and re-run on baseline. |
| **Stale-note surfacing rate** | Weekly: for production queries where multiple pages share a frontmatter `entity:` value, count how often the older page ranks at index 0 | If >25% of such queries surface stale notes, add a `recency_boost` factor to the hybrid retriever (deferred to a Phase 3 retrieval tuning). |
| **Cost per invocation trend** | Daily aggregate of mean cost_usd per `brain.query` invocation | If mean drifts above `$0.04`, query intent routing (cheap-tier filter for simple queries) may be misconfigured — investigate the gpt-4o-mini routing path. |
| **Conversation parity audit** | Weekly: sample 20 paired (MCP, REST) invocations of identical queries from production logs; diff resulting `messages` rows | If divergence rate >1%, investigate transport-specific bugs. |
| **Wikilink extraction stability** | After every page write, log `links_added`, `links_removed`, `links_unchanged` deltas | If a write produces large churn (>20 link changes for a single edit), inspect — may indicate a parser regression. |
| **Phoenix trace integrity** | Daily: sample 100 trace IDs from `agent.run` parent spans; assert every trace has the expected span shape | If any traces are missing child spans (e.g., `tool.*` missing), instrumentation has regressed — fix the span helper. |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (self-hosted; inherited from Phase 2a). Phase 2b extends instrumentation with three custom span categories propagated via OpenTelemetry to the same Phoenix instance at `http://localhost:6006/v1/traces`:

- `agent.run` — parent span per agent invocation. Attributes: `agent.query` (first 200 chars), `agent.user_id`, `agent.model`, `agent.status` (final result.status), `agent.iteration_count`, `agent.tool_call_count`, `agent.cost_usd`, `agent.duration_ms`. One per `brain.query` / `POST /api/v1/query`.
- `agent.iteration.{n}` — child span per ReAct iteration. Attributes: `agent.iteration` (int), `agent.tool_calls_in_iter` (count). Wraps the THINK + ACT + OBSERVE for one cycle.
- `tool.{name}` — grandchild span per tool dispatch. Attributes: `tool.name`, `tool.args_json` (truncated), `tool.retried` (bool), `tool.skipped` (bool), `tool.skip_reason` (str | null), `tool.error` (str | null). Joined to the parent iteration span by trace_id.

LiteLLM auto-instrumentation (already wired by Phase 2a) emits `llm.completion` spans as children of `agent.iteration.{n}` automatically — no extra code needed. Cost (`response.usage.total_cost`) is attached as `llm.cost_usd` on the LiteLLM span.

**Key Metrics to Track:**

1. `agent_invocations_total{status}` — counter, labelled by `success` / `success_with_warnings` / `tool_error` / `max_iterations_reached` / `no_local_knowledge`. Production health signal.
2. `agent_iteration_count_histogram` — distribution of `len(tool_traces)` per invocation. Buckets: 1, 2, 3, 4, 6, 8, 10. Target: p50 ≤ 4, p95 ≤ 7.
3. `agent_cost_usd_histogram` — distribution of `cost_usd` per invocation. Target: p50 ≤ $0.02, p95 ≤ $0.06. Alert at p95 > $0.10.
4. `agent_latency_ms_histogram` — end-to-end (FastAPI entry → response). Target: p50 < 3s, p95 < 8s.
5. `agent_tool_failure_rate{tool_name}` — counter of `skipped OR retried`, divided by total invocations of that tool. Per-tool quality signal.
6. `agent_brain_first_violations_total` — counter incremented every time the external-tool gate fires. Should be near zero in production; non-zero signals system-prompt drift or model misalignment.
7. `agent_no_local_knowledge_rate` — fraction of invocations returning `no_local_knowledge`. Tracks empty-vault transparency in production; calibrates against vault size growth.
8. `agent_conversation_persistence_lag_ms` — time between `run_react_loop()` return and `persist_agent_invocation()` commit. Should be < 100ms; sustained higher signals DB contention.
9. `links_extracted_per_page_write` — histogram of link count delta on each page write. Distribution shifts indicate parser regressions.
10. `graph_traverse_query_duration_ms` — histogram of `brain.graph.traverse` recursive CTE wall-clock time. Per-user vault growth surfaces here.

**Alert Thresholds:**

- `agent_invocations_total{status="tool_error"}` rate > 2% over a 1h window → P2 page: critical tool is failing in production; investigate top-failing `tool_name` from `agent_tool_failure_rate`.
- `agent_invocations_total{status="max_iterations_reached"}` rate > 1% over a 24h window → P3 alert: agent is hitting the ceiling; possible model regression or prompt drift.
- `agent_cost_usd_histogram` p95 > $0.10 sustained for 1h → P2 page: cost regression; investigate iteration count and model routing.
- `agent_latency_ms_histogram` p95 > 12s sustained for 15min → P2 page: investigate Phase 2a search latency (likely upstream) and DB pool exhaustion.
- `agent_brain_first_violations_total` > 0 in any 1h window → P1 page (zero-tolerance): the external-tool gate fired, meaning the agent attempted an external call. Either a bug or a prompt regression — both block release.
- `agent_no_local_knowledge_rate` drops below 2% over 24h for a user whose vault was previously producing ≥10% → P3 alert: possible confabulation regression; sample and human-review.
- `agent_conversation_persistence_lag_ms` p95 > 500ms → P3 alert: DB contention or RLS enforcement bug.
- `links_extracted_per_page_write` p95 > 50 per single edit → P3 alert: wikilink parser may be matching too broadly; inspect last parser change.
- `graph_traverse_query_duration_ms` p95 > 2s sustained → P3 alert: per-user graph has grown beyond efficient traversal; consider depth-limit defaults or B-tree index audit.

**Smart Sampling Strategy:**

Sample interactions for human review when:

- `result.status == "tool_error"` — top review priority; every critical failure should be inspected within 24h.
- `result.status == "max_iterations_reached"` — investigate whether the query was malformed or the agent was thrashing; promote pathological cases into the golden suite.
- `len(tool_traces) > 7` and `status == "success"` — high-iteration successes are candidates for either prompt improvement or new tool addition.
- `warnings != []` AND `result.status == "success_with_warnings"` — non-critical tool failures that succeeded; sample for whether the warning was material to the user's answer.
- Citation count in `messages.citations` is empty AND `result.status == "success"` — citation drift indicator; sample to catch system-prompt regressions before the citation density flywheel flags them in aggregate.
- `tool_traces[0].tool_name != "brain.search"` AND `result.status == "success"` — brain-first violations that escaped the gate; should be zero, every occurrence is reviewed.
- Any invocation where the same `tool_name` appears > 3 times in `tool_traces` — possible tool-call loop; promote to golden suite as a "loop detection" probe.
- 1% random sample across all `success` invocations — baseline drift detection independent of signal filters.
- Any production query where the cited slug is later edited or deleted within 1h — possible mis-citation discovered by user; auto-flag for review.
