## 1. System Classification

**System Type:** Hybrid RAG (custom pgvector retrieval pipeline with LLM routing layer)

**Description:**
Smart Copilot's intelligence layer: a hybrid retrieval pipeline that accepts natural-language queries from AI agents (Claude Desktop, Claude Code, Hermes) and returns grounded, cite-backed responses sourced from a personal knowledge vault. The system routes all LLM/embedding calls through a tiered LiteLLM router (cheap/balanced/strong), splits vault pages into typed chunks (truth/event/summary/detail/enrichment) stored in pgvector HNSW, retrieves candidates via both cosine similarity and BM25 tsvector, and fuses results using Reciprocal Rank Fusion with compiled-truth boost. A rule-based intent classifier routes queries to retrieval mode; multi-query expansion fires on threshold. "Good" means: retrieved chunks are from the actual vault, ranked by relevance and truthfulness, with no hallucinated content, returned in under 300ms p95.

**Critical Failure Modes:**
1. **Hallucinated chunk attribution** — system returns content that is not present in the vault, causing agents to cite fabricated information
2. **Cold-start blind spot** — when HNSW index is empty or embedding queue lags, system silently returns no results instead of falling back to FTS
3. **Provider key leakage** — per-user encrypted LLM provider keys exposed in logs, error messages, or LLM call metadata
4. **RLS bypass in retrieval path** — cross-user vault content returned due to missing `SET app.current_user_id` in chunker, embedder, or search path
5. **Cost runaway** — unbounded multi-query expansion or misconfigured model tier routes cheap queries through the strong (expensive) model

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / Personal knowledge management (PKM)

**User Population:** Individual developers and knowledge workers querying their own personal vault of notes, compiled truths, and timeline events through AI agents (Claude Desktop, Claude Code, CLI). Self-hosted, homelab deployment context. Users trust the system to surface their own knowledge accurately — any retrieval error is directly attributable.

**Stakes Level:** Medium (personal productivity context; no direct safety/health/financial consequence, but correctness matters — wrong answers erode trust and cause wasted effort acting on false information)

**Output Consequence:** AI agents act on retrieved chunks to answer questions, generate summaries, or inform decisions. Hallucinated or misranked chunks directly corrupt agent responses. Users have no secondary fact-checking mechanism — if the vault says it, they believe it.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|-----------|----------------------|-------------------|--------|--------|
| **Source faithfulness** | Every claim in the response traces to a specific chunk with chunk_id and page_slug | Response contains content not present in any retrieved chunk | High | PKM practitioner standard |
| **Compiled-truth priority** | Compiled-truth chunks (kind=truth) rank above timeline events for factual queries | An older timeline event outranks the compiled-truth version of the same fact | High | Phase CONTEXT.md D-03, D-13 |
| **Retrieval coverage** | All relevant chunks returned regardless of storage path (vector, BM25, or FTS fallback) | Important chunk missed because HNSW index was cold and no fallback triggered | High | D-10 |
| **BM25/vector calibration** | BM25 and vector scores contribute proportionally; RRF fusion produces stable rankings across repeated queries for the same vault content | One channel dominates entirely (e.g., BM25 contribution <5% of top-K), or RRF k=60 default inflates low-ranked results on a small personal vault where k=20–30 would concentrate signal | Medium | RAG practitioner benchmarks: hybrid RRF adds ~1.3% NDCG over BM25 naively; properly tuned hybrid adds 7.5%+ (arxiv 2604.01733) |
| **Stale content annotation** | Results from pages whose compiled-truth is stale are flagged with `{stale: true, stale_days: N}` | Stale results surfaced without annotation, misleading the agent | Medium | D-12, D-13 |
| **Deduplication quality** | Near-identical chunks (cosine ≥ 0.92) collapsed to highest-scoring representative | Same paragraph returned 3 times under different chunk_ids | Low | D-14 |
| **LLM cost per query** | Multi-query expansion fires only when threshold met; cheap tier used for expansion | Strong-tier model called for query expansion on simple 3-word queries | Medium | D-08, D-12 |
| **Answer completeness** | When a user's vault contains all the information needed to answer a query, all necessary chunks are surfaced and none are silently dropped by the per-page cap or dedup layers | Vault contains the answer across 2 chunks on the same page, but per-page cap (max 1) silently drops the second; agent gives a partial answer that sounds complete | Medium | Human-centered RAG evaluation framework (arxiv 2509.26205); PKM practitioner reports on chunk boundary fragmentation |

### Known Failure Modes in This Domain

- **Embedding coverage lag**: New pages indexed async (APScheduler); queries during the indexing window miss recently added content. FTS fallback handles this but reveals coverage gap to callers via `search_type="fts_v1"`.
- **Compiled-truth staleness**: If `compiled_truth_updated_at` lags `latest_timeline_ts` by more than `SMARTCOPILOT_STALE_DAYS`, the ranked-first truth chunk may be outdated. System annotates stale but still returns it.
- **BM25/vector score skew on domain jargon**: Vault-specific terms (Obsidian-style wikilinks, custom project names) may rank poorly on BM25 but highly on vector similarity. Mis-calibrated RRF weights amplify this.
- **Per-page diversity cap** at max 1 chunk can silently drop highly relevant secondary chunks from the same page (e.g., a long compiled-truth section).
- **Intent classifier false positives**: Rule-based graph-intent routing (pattern matching on `[[Entity]]`) may trigger graph-first path on literal text that happens to contain brackets.
- **Chunk boundary fragmentation on long compiled-truth sections**: A compiled-truth section spanning multiple logical paragraphs gets split at a 512-token hard boundary mid-argument. The retrieved chunk is syntactically complete but semantically incomplete — it sounds authoritative but is missing the qualifying condition written in the next chunk. Documented as a PKM-specific failure mode in practitioner Obsidian+RAG deployments (dasroot.net, dev.to 2025–2026).
- **Query expansion redundancy**: Multi-query expansion produces 3 paraphrases that are semantically near-identical to the original query (e.g., restating the same noun phrase 3 ways). Expansion fires (threshold met), LLM cost is incurred, but all 4 retrieval runs return the same top-K chunks — recall does not improve. Distinct from intent classifier false positives: the classifier correctly routes to expansion, but the LLM generates low-diversity paraphrases.

## 2. Framework Decision

**Selected Framework:** LiteLLM 1.x (library mode, in-process import)

**Version:** `litellm>=1.40,<2.0` (pin minor series; avoid proxy/server mode entirely)

**Rationale:**
Phase 2a is a fully specified custom retrieval pipeline — chunker, RRF fusion formula, intent classifier, and embedding batching are all deterministic Python services. Every architectural component is already decided in CONTEXT.md: pgvector HNSW for vectors, `chunks.tsv` tsvector for BM25, custom RRF formula, rule-based intent classifier. Adding LlamaIndex or LangChain would impose abstraction over components already designed to spec and conflict with the PostgreSQL-only, no-new-infrastructure constraint. LiteLLM is the only genuinely new AI dependency: it handles multi-provider routing (OpenAI / Anthropic / DeepSeek), per-user API key injection, cost tracking hooks, and the `AsyncEmbedding` / `acompletion` async API that the embedding worker and query expansion need. It is already committed as a project decision in CONTEXT.md canonical_refs.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex | Would replace custom pgvector/BM25 retrieval with its own pipeline abstractions, conflicting with the no-external-RAG-framework constraint and the already-spec'd chunker/RRF logic |
| LangChain | Heavy abstraction overhead with no benefit over direct LiteLLM + FastAPI services; retrieval quality improvement doesn't apply when retrieval is custom |
| Haystack 2.x | Declarative pipeline abstraction not needed — pipeline stages are already defined as Python services; adds a new infrastructure layer for no gain at this stage |
| OpenAI Agents SDK | OpenAI vendor lock-in; LiteLLM already provides multi-provider routing that supersedes it |

**Vendor Lock-In Accepted:** No — LiteLLM provides model-agnostic routing across OpenAI, Anthropic, DeepSeek, and local models. The retrieval pipeline (pgvector + BM25 + RRF) has zero AI vendor dependency.

### Entry Point Pattern
```python
# LLM router: tier-based completion call
async def llm_complete(
    prompt: str,
    tier: Literal["cheap", "balanced", "strong"],
    user_api_keys: dict[str, str],
    op_ctx: OperationContext,
) -> str:
    model_id = TIER_MODELS[tier]                        # resolved from settings
    provider = model_id.split("/")[0]
    api_key = user_api_keys.get(provider) or settings.system_api_keys[provider]
    
    response = await acompletion(
        model=model_id,
        messages=[{"role": "user", "content": prompt}],
        api_key=api_key,                                # never log this
        metadata={"user_id": str(op_ctx.user_id)},     # for cost tracking
    )
    await record_llm_usage(op_ctx, model_id, response)
    return response.choices[0].message.content

# Embedding router: batch-aware
async def embed_chunks(
    texts: list[str],
    user_api_keys: dict[str, str],
) -> list[list[float]]:
    provider_key = user_api_keys.get("openai") or settings.system_api_keys["openai"]
    response = await aembedding(
        model="text-embedding-3-small",
        input=texts,                                    # batched, max 100
        api_key=provider_key,
    )
    return [item["embedding"] for item in response.data]
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `acompletion` | Async LLM call; model-agnostic | Every query expansion and future answer synthesis call |
| `aembedding` | Async embedding call (batched) | Embedding worker for chunks (100 per batch) |
| `completion_cost()` | Post-call cost calculator | After every call to populate `llm_usage.cost_usd` |
| `litellm.callbacks` | List of `CustomLogger` instances (or string names for built-ins) called after each response | Register `UsageRecorder()` here for DB cost recording; sync `log_success_event` and async `async_log_success_event` both available |
| `metadata` | Per-call dict passed through to callbacks | Carries `user_id` for RLS-safe cost attribution |

### Common Pitfalls

1. **Global `os.environ` key injection** — never set `OPENAI_API_KEY` globally; always pass `api_key=` per-call. Global keys are per-process, not per-user, and will cross user boundaries.
2. **Sync `completion()` inside async handlers** — using `litellm.completion()` (sync) inside an `async def` blocks the event loop. Always use `acompletion()` / `aembedding()` in async contexts.
3. **Cost tracking without `metadata`** — `completion_cost()` returns a float but doesn't attribute it to a user unless you carry `user_id` through the `metadata` dict. Wire it at call time, not retroactively.
4. **Unhandled `litellm.exceptions.AuthenticationError`** — per-user key can be invalid/expired; catch and surface as a user-facing error (not 500), clearing the cached key.
5. **`aembedding` rate limits** — OpenAI `text-embedding-3-small` has per-minute token limits; batching at 100 chunks is safe but add exponential backoff on `litellm.exceptions.RateLimitError` (maps to `openai.RateLimitError`).
6. **Sync `log_success_event` in async context** — `CustomLogger.log_success_event` is synchronous; calling it from an `acompletion` callback inside an async loop can block. Use `async_log_success_event` instead when the callback performs I/O (e.g., async SQLAlchemy `INSERT` into `llm_usage`).

## 4. Implementation Guidance

**Model Configuration:**
- Cheap tier: `openai/gpt-4o-mini` or `deepseek/deepseek-chat` — query expansion (3 paraphrases), classification assistance
- Balanced tier: `openai/gpt-4o` or `anthropic/claude-sonnet-4-6` — future answer synthesis
- Strong tier: `openai/o3` or `anthropic/claude-opus-4-7` — complex reasoning tasks (Phase 3+)
- Embedding model: `openai/text-embedding-3-small` (1536 dimensions, matches `VECTOR(1536)` column)
- Temperature: 0.3 for query expansion (need diversity but not randomness); 0.0 for classification
- Max tokens: 200 for query expansion output (3 paraphrases); streaming not needed for Phase 2a

**Core Pattern:**
Service layer is transport-agnostic (`OperationContext` in, domain objects out). The `llm/router.py` is the only entry point for LiteLLM calls — all other services call the router, never `litellm` directly. Router records to `llm_usage` via `success_callback`. Retriever calls pgvector and tsvector directly via SQLAlchemy async sessions with `session_with_rls()`.

**Tool Use:**
No agentic tool use in Phase 2a — LiteLLM is used for completions and embeddings only. Tool calling deferred to Phase 2b (ReAct agent). Phase 2a's LiteLLM usage is purely: `aembedding` (embed worker) + `acompletion` (query expansion).

**State Management:**
All state in PostgreSQL. Chunks stored in `chunks` table with embeddings in `chunks.embedding VECTOR(1536)`. Embedding job progress tracked in `system_config` table. No in-memory state survives process restart. LiteLLM itself is stateless per-call — no session management needed.

**Context Window Strategy:**
Phase 2a does not synthesize answers (deferred to Phase 2b/3). Context window is only relevant for query expansion: system prompt + 1 query + instruction ≈ 200 tokens input, 200 tokens output — well within cheap-tier limits. Chunk size (512 tokens, 50-token overlap from D-01) is calibrated to stay within `text-embedding-3-small`'s 8191 token limit with large margin.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

LiteLLM does not enforce Pydantic output schemas natively, but query expansion output should be validated before use. Use `instructor` or manual JSON parsing with Pydantic:

```python
from pydantic import BaseModel, field_validator

class QueryExpansion(BaseModel):
    paraphrases: list[str]

    @field_validator("paraphrases")
    @classmethod
    def exactly_three(cls, v: list[str]) -> list[str]:
        if len(v) != 3:
            raise ValueError(f"Expected 3 paraphrases, got {len(v)}")
        return v

async def expand_query(query: str, router: LLMRouter) -> list[str]:
    raw = await router.complete(
        prompt=EXPANSION_PROMPT.format(query=query),
        tier="cheap",
        response_format={"type": "json_object"},  # litellm passthrough to provider
        # NOTE: {"type": "json_object"} enforces JSON shape only — no schema validation.
        # For OpenAI-backed cheap tier, prefer json_schema with model_json_schema():
        #   response_format={"type": "json_schema", "json_schema": {
        #       "name": "query_expansion", "strict": True,
        #       "schema": QueryExpansion.model_json_schema()}}
        # Anthropic models do not support json_schema mode; use json_object + validate.
    )
    try:
        data = QueryExpansion.model_validate_json(raw)
        return data.paraphrases
    except ValidationError:
        # Retry once with stricter prompt; fall back to [query] if second attempt fails
        return [query]
```

### Async-First Design

LiteLLM's `acompletion` and `aembedding` are true async — they use `httpx.AsyncClient` internally. Key rules:
- **Always `await`** in async FastAPI routes and APScheduler async jobs.
- **Never run `litellm.completion()` (sync) inside `async def`** — it will block the event loop via internal `asyncio.run()`.
- **Embedding worker is an APScheduler async job** (not inside uvicorn) — use `asyncio.get_event_loop()` correctly or let APScheduler handle the loop.
- **Use `async_log_success_event` for async I/O in callbacks** — `CustomLogger` provides both `log_success_event` (sync) and `async_log_success_event` (async). Use the async variant when recording to `llm_usage` via SQLAlchemy async session; using the sync variant for DB writes blocks the event loop.
- **Do not stream in Phase 2a** — no end-user UI consuming tokens; `await acompletion(stream=False)` is correct.
- Batch embedding: `await aembedding(input=texts[:100])` — 100 chunks saturates the API without hitting per-minute token limits.

### Prompt Engineering Discipline

```python
# System prompt: defines the task contract — never mixes with user content
EXPANSION_SYSTEM = """You generate search query paraphrases for a personal knowledge vault.
Output exactly 3 alternative phrasings of the user's query as JSON: {"paraphrases": ["...", "...", "..."]}
Do not add explanation. Do not alter meaning. Keep each paraphrase under 20 words."""

# User prompt: carries only the query — no system instructions
EXPANSION_USER = "{query}"
```
- Keep system prompts in constants, not f-strings constructed at runtime.
- Token budget for cheap tier: system ≤ 150 tokens, user ≤ 50 tokens, output ≤ 200 tokens.
- No few-shot examples in Phase 2a (query expansion is simple enough; add if hallucination rate >5%).

### Context Window Management

Phase 2a does not pass retrieved chunks to an LLM (answer synthesis is Phase 2b/3). The only LLM context management concern is query expansion:
- Input: system prompt (~100 tokens) + user query (≤ 50 tokens) = ~150 tokens total
- Output: 3 paraphrases (~60 tokens) — well within cheap-tier 4096 token limit
- No truncation needed.

For the embedding path: tiktoken boundary calculation (D-01) ensures chunks stay under 512 tokens. Fallback is character estimate at 4 chars/token. The `text-embedding-3-small` limit is 8191 tokens — chunks at 512 tokens have 16× headroom.

### Cost and Latency Budget

| Operation | Model | Est. Input Tokens | Est. Cost/Call | Frequency |
|-----------|-------|------------------|----------------|-----------|
| Query expansion | gpt-4o-mini | ~150 | ~$0.000023 | When query ≥ 6 words |
| Chunk embedding (batch 100) | text-embedding-3-small | ~51,200 | ~$0.010 | On page write (async) |
| Single chunk re-embed | text-embedding-3-small | ~512 | ~$0.0001 | On chunk update |

- Caching: LiteLLM has built-in in-memory caching; enable for query expansion to avoid redundant calls on repeated identical queries:
  ```python
  from litellm.caching import Cache
  litellm.cache = Cache()  # in-memory; no Redis dependency needed for homelab
  # Pass caching=True and ttl=3600 per-call (ttl is in seconds):
  response = await acompletion(..., caching=True, ttl=3600)
  ```
  This covers repeated identical queries (e.g., same `@web` prefix check within the same hour).
- Model routing gate: intent classifier runs before expansion — only queries passing the threshold call the cheap LLM. Short/precise queries never touch the LLM layer.

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail or 1-5) | Measurement Approach | Priority |
|-----------|--------------------------|---------------------|----------|
| **Retrieval Recall** | Pass: ground-truth chunk appears in top-K results for labeled query set. Fail: ground-truth chunk absent from top-K | Code — compare chunk_ids against labeled set | Critical |
| **Retrieval Precision** | 1-5: fraction of top-K results that are relevant (labeled by vault owner). 5=all relevant, 1=< 40% | Code + Human (initial labeling) | Critical |
| **Context Faithfulness** | Pass: every SearchResultItem.content is verbatim or direct substring of a vault chunk. Fail: any fabricated content | Code — substring check against chunks table | Critical |
| **Answer Completeness** | Pass: for queries whose ground-truth answer spans ≥2 chunks on the same page, all required chunks are surfaced in top-K (no silent drops by per-page cap or dedup). Fail: a labeled "completeness query" returns only 1 of N required chunks AND the missing chunk would have ranked in top-K but was dropped by the per-page cap or dedup layers. | Code — labeled subset of reference dataset; assert top-K contains ALL required chunk_ids for completeness queries; cross-check that dropped chunk_ids did not appear in pre-cap candidate list | High |
| **RRF Fusion Rank Quality** | 1-5: compiled-truth chunks (kind=truth) rank above timeline events for factual queries. 5=always, 1=never | Code — check kind field of top result for factual query set | High |
| **RRF k Calibration** | Pass: on the reference dataset, mean NDCG@10 at the configured `SMARTCOPILOT_RRF_K` is within 2% of the best-performing k in `{20, 30, 40, 60}`. Fail: default k=60 underperforms k=20–30 by >5% NDCG on the small-vault reference set (research finding: arxiv 2604.01733 + small-corpus practitioner reports). | Code — parameterized eval sweep across k values; emit ranked table; require chosen k to be within margin of best | High |
| **Query Expansion Diversity** | Pass: when expansion fires, the 3 paraphrases yield a top-K union (across the 4 retrieval runs: original + 3 paraphrases) that is ≥30% larger than the original-query top-K alone. Fail: paraphrase union adds <10% new chunk_ids — expansion incurred LLM cost without improving recall (redundancy failure mode from Section 1b). | Code — execute retrieval 4× (original + each paraphrase); compute set-union delta; LLM judge optional second check on paraphrase semantic distinctness | Medium |
| **Cold-Start Fallback** | Pass: when HNSW is empty, search_type=fts_v1 and result count > 0. Fail: empty results with no fallback | Code — integration test with empty HNSW index | High |
| **BM25 Channel Contribution** | Pass: at least 20% of top-K results sourced via BM25 path (retrieval_paths includes "bm25"). Fail: vector dominates entirely | Code — inspect retrieval_paths field | Medium |
| **Stale Annotation Accuracy** | Pass: results from pages where compiled_truth_updated_at lags > STALE_DAYS carry stale=true. Fail: stale content not annotated | Code — compare timestamps against annotation | High |
| **LLM Cost Per Query** | Pass: expansion-enabled queries cost ≤ $0.001. Fail: any query costs > $0.01 | Code — check llm_usage table cost_usd | Medium |
| **Deduplication Effectiveness** | Pass: no two results in top-K have cosine similarity ≥ 0.92. Fail: near-duplicates present | Code — post-hoc cosine check on result set | Medium |
| **Provider Key Safety** | Pass: no api_key appears in logs, error messages, or llm_usage records. Fail: key leaked | Code — grep log output for key patterns in test run | Critical |

```python
        return
    resource = Resource.create({"service.name": service_name})
    provider = TracerProvider(resource=resource)
    provider.add_span_processor(
        BatchSpanProcessor(
            OTLPSpanExporter(endpoint=f"{settings.phoenix_endpoint}/v1/traces")
        )
    )
    trace.set_tracer_provider(provider)
    LiteLLMInstrumentor().instrument()         # auto-trace every acompletion/aembedding
```
- Custom retrieval spans (vector query, BM25 query, RRF fusion, dedup layers) are added manually via `tracer.start_as_current_span()` in `rag/retriever.py` and `rag/reranker.py`. Phoenix groups them under the parent search request span by trace_id propagation.
- LiteLLM cost (`response.usage.total_cost`) is added to its span as a span attribute (`llm.cost_usd`) so Phoenix's cost dashboard works without parallel `llm_usage` queries.

### Reference Dataset

**Size:** 20 examples to start; expand to 50 after first month of production use

**Composition:**
- 4 factual queries targeting compiled-truth chunks (kind=truth) — validate compiled-truth ranking priority
- 4 timeline-style queries (what happened on X date / last week) — validate event chunk retrieval
- 3 multi-keyword queries that benefit from BM25 (exact domain terms, project names) — also exercise BM25/vector calibration
- 3 cold-start simulation queries (run against empty HNSW, verify FTS fallback)
- 2 graph-intent queries (contain `[[Entity]]` patterns) — validate intent classifier routing (and false-positive guard for literal brackets)
- 2 **completeness queries** (ground-truth answer spans ≥2 chunks on the same page) — exercise per-page cap behavior; the dataset must record ALL required chunk_ids, not just one
- 1 **chunk-boundary fragmentation query** (ground-truth answer requires reading a 512-token boundary; both adjacent chunks must rank in top-K) — exercise overlap window adequacy
- 1 **expansion-redundancy probe query** (≥6 words, question-word prefix → triggers D-08 expansion gate) — used by the Query Expansion Diversity eval to measure paraphrase union-delta

Edge-case probes layered on top (do not consume primary slots):
- Very short query (≤ 2 words) included within the timeline/factual set to confirm expansion gate skips it (D-08)
- Very long query (≥ 20 words) within the question-word set to confirm expansion fires without truncation
- One adversarial query containing `[[brackets]]` as literal text (not a wikilink) — guards intent classifier false-positive

**Labeling:**
Vault owner labels ground-truth relevant chunk_ids for each query. For **completeness queries**, owner labels the *complete set* of required chunk_ids; eval asserts top-K is a superset, not just intersection. For **expansion-redundancy probes**, owner pre-computes the top-K from the original query alone so the diversity eval has a reference set to compute union-delta against. LLM judge (Claude Sonnet) used for faithfulness scoring and paraphrase-distinctness scoring at scale, calibrated against vault owner spot-checks (target correlation ≥ 0.8 before relying on LLM judge alone). All labels stored in `tests/fixtures/retrieval_reference.json` with schema:
```json
{
  "query_id": "...", "query": "...", "tags": ["compiled_truth"|"completeness"|"expansion_probe"|...],
  "required_chunk_ids": ["..."],          // must ALL appear in top-K for completeness queries
  "expected_top_k": ["..."],              // ordered ground truth for recall/precision
  "expected_search_type": "hybrid_v1",
  "original_top_k_baseline": ["..."]      // populated for expansion_probe queries only
}
```

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Provider key scrub** | Every LiteLLM call's `api_key` kwarg before logging | Redact key from all log output; log `[REDACTED]` |
| **RLS enforcement** | Every DB session in chunker, embedder, retriever, reranker | `SET app.current_user_id` + `RESET` in `finally:` — reject query if session lacks user_id |
| **Cost ceiling per query** | `llm_usage.cost_usd > $0.01` for a single search request | Log warning + return existing results without further LLM expansion; never block the search response |
| **Empty result guard** | Search returns 0 results after all retrieval paths | Return `{results: [], status: "no_results", search_type: actual_path}` — never 500 |
| **Expansion gate** | Intent classifier threshold check before calling cheap LLM | Short/precise queries skip expansion entirely (D-08); gate is deterministic, no LLM needed |
| **Expansion diversity floor** | Before issuing the 3 paraphrase retrievals, compute pairwise cosine on paraphrase embeddings; if all pairs >0.95, treat as redundant | Skip the extra retrievals; record `expansion_skipped="low_diversity"` in trace; saves vector ANN queries |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Retrieval recall trend** | Weekly batch eval of last 7 days' queries against reference dataset | If recall drops > 5% week-over-week, investigate embedding model drift or index health |
| **search_type distribution** | Daily aggregate: ratio of hybrid_v1 vs fts_v1 vs bm25_v1 | If fts_v1 > 20% of queries, embedding pipeline is lagging — investigate APScheduler job |
| **llm_usage cost trend** | Daily aggregate: total cost_usd by tier, by user | Alert if cheap-tier cost spikes > 2× 7-day average (expansion threshold may have regressed) |
| **Stale annotation rate** | Weekly sample: % of results carrying stale=true | High rate (>30%) indicates compiled-truth indexing is lagging — surface to vault maintenance routine |
| **RRF k vs corpus-size fit** | Monthly: re-run `eval_rrf_k_sweep.py` over current vault; chart best-k vs `count(chunks)` per user | If recommended-k drifts ≥10 from configured `SMARTCOPILOT_RRF_K`, propose new default (small-vault optimum k=20–30 from arxiv 2604.01733) |
| **Expansion redundancy rate** | Weekly: sample expansion-firing queries; compute mean top-K union-delta | If union-delta <0.15 for >25% of expansions, expansion prompt is generating low-diversity paraphrases — retune system prompt or raise temperature toward 0.5 |
| **Answer completeness rate** | Weekly: re-run completeness subset of reference dataset | If per-page cap drops a required chunk in >10% of completeness queries, raise per-page cap from 1 to 2 or revisit cap logic (Section 1b: known PKM failure mode) |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (self-hosted; deploy as either supervisord process inside the smart-copilot container or a Docker sidecar — both documented in Section 5 Eval Tooling). LiteLLM auto-instrumented via `openinference-instrumentation-litellm`; custom retrieval spans added manually in `rag/retriever.py` and `rag/reranker.py` and propagated to Phoenix via OTLP HTTP exporter to `http://localhost:6006/v1/traces`. Single trace per `brain.search` request joins LiteLLM expansion span + vector ANN span + BM25 span + RRF fusion span + dedup span by trace_id.

**Key Metrics to Track:**
1. `search_latency_p95` — target < 300ms end-to-end for hybrid_v1 path
2. `embedding_queue_depth` — chunks awaiting embedding; sustained >100 triggers cold-start fallback alert
3. `llm_cost_per_query_usd` — per-query cost attribution from `llm_usage` table; alert at > $0.01
4. `retrieval_path_distribution` — ratio of hybrid_v1 / bm25_v1 / fts_v1 per day
5. `rls_violation_count` — any DB session missing `app.current_user_id` (should be zero; any non-zero is a P1 bug)
6. `corpus_size_per_user` (count(chunks) grouped by user_id) — fed into RRF k calibration flywheel; surfaces when a user crosses small-vault → medium-vault thresholds (≈1k chunks) where default k=60 becomes appropriate
7. `expansion_paraphrase_diversity` — span attribute on each expansion event: mean pairwise cosine distance across the 3 paraphrase embeddings (lower = redundant; tracks Section 1b redundancy failure mode)
8. `per_page_cap_dropped_count` — counter incremented when reranker dedup/per-page cap drops a chunk that would have ranked in top-K; production signal for the answer-completeness flywheel

**Alert Thresholds:**
- `search_latency_p95 > 500ms` sustained for 5 minutes → investigate HNSW index health
- `embedding_queue_depth > 500` → APScheduler embed worker may be down
- `llm_cost_per_query_usd > 0.05` → query expansion may be firing on all queries (regression in intent classifier threshold)
- `fts_v1 fraction > 30%` for a user → their HNSW index is cold; trigger manual re-index
- `rls_violation_count > 0` → page on-call immediately
- `corpus_size_per_user` crosses 1000 chunks and configured `SMARTCOPILOT_RRF_K` still at small-vault default (20–30) → surface RRF k re-tune recommendation
- `expansion_paraphrase_diversity` mean < 0.05 (cosine distance) over a 24h window → expansion prompt is degenerate; retune temperature/prompt
- `per_page_cap_dropped_count` > 0 with same page_slug repeating across users → systemic completeness regression; investigate cap policy

**Smart Sampling Strategy:**
Sample interactions for human review when:
- `search_type = "fts_v1"` (cold-start path — surface to vault maintenance)
- Result count = 0 (empty results — highest review priority)
- `retrieval_paths` missing "bm25" (BM25 channel may be broken)
- Query contains `[[...]]` but `search_type != "graph_v1"` (intent classifier missed a graph query)
- `stale = true` in top result (user may be acting on outdated information)
- `expansion_skipped="low_diversity"` (expansion gate fired but paraphrases were redundant — feeds expansion-redundancy flywheel)
- `per_page_cap_dropped_count > 0` on a query labeled with `tags` containing `completeness` (validates the production signal against the reference dataset)
